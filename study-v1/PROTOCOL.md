# Prospective development study v1

This is a small methodological experiment, not a confirmed formal OpenRSI task
contract, a strong-model baseline, or a runner-native RSI trajectory. The scope
is one canonical cycling-pelican asset and one reusable-method update.

## Fixed workload and exposure

`scenes.json` delivers exactly two prior fixtures, three development fixtures and
one new compound transfer fixture. Spatial clearance is measured from exported
mesh vertices across the sampled animation states. The new fixture combines
stricter ceiling, width and triangle constraints with the same docking interface.
It tests a new combination/parameter setting within this asset family; it is not
an unseen asset family or private benchmark split.

Each development trial starts from the same canonical source and receives its
current brief plus the two prior requirements, one model call and no repair.
The method writer receives all three development scripts/results, including
failures, plus the canonical source. It receives no transfer brief, assets or
feedback. Its output is a non-executable instruction policy of at most 2,500
characters. One method-writing call is allowed, with no manual editing or silent
format repair. An invalid policy ends the policy condition as unscored.

The valid policy must be frozen before either transfer condition starts.
Both independent adaptation and policy-assisted adaptation start from the exact
same canonical source and four canonical images. Each receives the transfer
brief and all prior/development retention requirements, with exactly two maximum
generation opportunities. The second sees its own first source and actual engine
feedback. Only the policy-assisted condition additionally receives the frozen
instructions. The independent condition cannot see development outputs or the
learned policy. Transfer is run independent first, then policy-assisted; service
state and model sampling are not controlled, so one pair is exploratory.

All generator and method-writing calls request `gpt-6-astra`, low reasoning,
180-second deadlines, web/tools disabled, and zero automatic retries. Planned
maximum: 3 development calls + 1 method call + 4 transfer calls = **8 calls**.
Method-development cost is reported separately; only transfer generation budgets
are matched. There is no claim of equal total research compute or multiple RSI
method-update rounds. Existing low reasoning is retained for a quick exploratory
comparison; calibration of the intended formal configuration remains pending.

## Candidate and fixed boundaries

The candidate is self-contained Blender Python generating one shared GLB. All
retention fixtures evaluate that exact GLB; this v1 does not implement distinct
per-scene adapters. The model authors geometry and animation. Godot supplies
input sampling, collision construction and measurement, without leg IK or motion
repair. Candidate code runs in the existing restricted CPU Blender container.

Models may reduce mesh complexity and reshape permitted static/visible geometry.
They must preserve the required parts, wheel/hip/crank interfaces and baked Ride
behavior. Docking requires a real visible plate and matching socket. Fixed
scenes, evaluator, units and scoring cannot be edited. Invisible proxies, deleted
parts and global shrink/translation are prohibited. Part-volume guards and
existing diagnostics are limited identity checks, not a complete semantic metric.

## Measurements, selection and failures

For each valid evaluated attempt report target-scene strict success separately
from retained-scene success and regressions relative to the canonical asset.
The development metric is the fraction of all required fixtures whose complete
checks pass. Select the attempt with most strict fixtures passed, then target
success, then the mean fraction of checks passed, retaining the earlier attempt
on an exact tie. Both first and selected outcomes are reported. Diagnostic counts
are correlated; hundreds of checks are not independent samples.

Syntactically invalid scripts, invalid GLBs, provider failures, timeouts and
infrastructure failures are preserved as unscored outcomes, not invented zero
rewards. A failed generation consumes its opportunity; an attributable generated
script failure may receive its one remaining declared repair call. Provider or
ambiguous infrastructure failures stop the condition. No replacement trials or
discarded fixtures. No official reward is defined by this local protocol.

## Calibration and interpretation

Before any model call, an explicitly developer-authored feasibility control must
pass every fixture. Broken-animation and missing-docking controls must fail.
Controls establish checker feasibility, never model scores. Freeze code, brief,
asset, image and scene hashes after this calibration and before model calls.
Keep complete native sessions, raw responses, scripts, GLBs and engine logs.
Do not revise thresholds or select a different workload after seeing model data.

One transfer pair cannot establish stable superiority, continual adaptation,
strong-model headroom or acceptance. If the baseline saturates, report that
result and design a separately versioned study rather than changing this score.
